## Этап 3. Управление сборками — блокирующий приоритет P0

Инцидент 27.11.2026: пять production MCP manifests содержали путь
из isolated build к tests/cwd-option.test.ts и параметры тестового Node.
После точечного восстановления manifests и перезапуска все 6/6 MCP
подключились (64 инструмента). Точный путь записи требует исследования.
Изоляция исходников сама по себе недостаточна.

- [ ] BUILD-001H — автоматизация сборки и проверка полной изоляции пользовательского состояния (часть BUILD-001).
- [ ] MCP-001 — устранить попадание тестовых launch arguments в production plugin cache; добавить регрессию.

Критерии BUILD-001: отдельный HOME/XDG, .zcode, plugin cache, временные
каталоги, отсутствие production credentials и доступа к production sessions;
неизменность production manifests и артефактов до/после тестов.
Рассмотреть отдельного пользователя zcodebuilder как усиление изоляции.
Не запускать полный набор тестов с production HOME fxagent.
Предыдущие экспериментальные PASS (4788 PASS/5 SKIP/0 FAIL, smoke и clean HOME)
не закрывают выявленный дефект изоляции; перепроверить после исправления.

Идентификатор BUILD-002 сохраняет исходный смысл: установка, версии и откат,
а не изоляция тестов. Изоляция входит в BUILD-001.

- [ ] BUILD-001 — изолированная сборка и тестирование.
- [ ] BUILD-002 — установка, версии и откат.
- [ ] UPDATE-001 — интеграция upstream.
- [ ] UPDATE-002 — регрессионная проверка обновлений.

## Этап 5. Устойчивость production

- [ ] MEM-001 (P0) — защита сервера от повторного OOM; согласовать бюджет памяти, поведение при лимите и восстановление.
- [ ] MEM-002 (P1) — исследовать накопление памяти CLI/дочерних процессов; длительный сеанс, compact, смена сессии, профилирование. 27.11 ядро завершило zcode-cli (около 6.62 GiB RSS и 3.13 GiB swap); глобальный OOM, утечка пока не доказана.
- [ ] AUTH-001 (P0) — проверить жизненный цикл исходного OAuth Access Token Z.AI и наличие refresh; ручной /login восстановил работу. Автоматический refresh исходного OAuth не подтверждён; не путать с существующим Business JWT refresh.
- [ ] AUTH-002 (P1) — безопасная классификация причин project_token_login_failed; не выводить токены, тела ответов или credentials.

## Этап 6. Биллинг и квоты

- [ ] BILL-001 (P1) — встроенная /bill для остатка DeepInfra прямо в чате, без вызова LLM и независимо от модели. Переиспользовать существующий deepinfra-billing после проверки интерфейса, единиц и доступных полей; read-only, тайм-аут, отметка свежести, безопасные ошибки, без передачи данных в контекст LLM. MVP: баланс, доступные расходы/лимит и статус; не выдумывать отсутствующие поля.
- [ ] USAGE-001 (P2) — /usage и возможное отображение квот Z.AI Coding Plan в TUI; проверить поддерживаемый API, отличать квоты от контекстного окна и ZCode Sites.

## Порядок работ и приёмка

1. BUILD-001/BUILD-001H и MCP-001 (единый блок изоляции); MEM-001 как срочная эксплуатационная защита по согласованию.
2. BUILD-002: установка проверенного кандидата, версия, rollback; затем live-приёмка BUG-04/05/06 на реальном CLI.
3. AUTH-001/002, MEM-002; BUG-06B/C только по результатам live-приёмки BUG-06A.
4. BUG-07/08/09, BILL-001, USAGE-001; UPDATE-001/002 после надёжной сборки и отката. Порядок внутри этапа уточнять по фактическим блокерам.

ROADMAP.md — единый индекс задач; BUGS.md — симптомы, доказательства и критерии;
BUILD.md — процедура сборки/изоляции; CHANGELOG.md — фактически принятые изменения;
UPSTREAM.md — сопровождение upstream. Не удалять незавершённые задачи при смене чата.
Сохранять существующие ID, разделять исходники, deployment и live-приёмку.
Локальные незакоммиченные документы task/build-001-isolated-build необходимо
сверить с этим обновлением перед merge, сохраняя уникальные детали обеих сторон.
Никаких изменений production в рамках этой документационной задачи.

Отметка исправления в исходниках не означает,
что изменение установлено и проверено в production.
